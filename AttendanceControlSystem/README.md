# سامانه کنترل حضور و غیاب

این پروژه یک برنامه وب **ASP.NET Core 8 MVC** است که احراز هویت را با کوکی انجام می‌دهد و داده‌ها را در SQLite نگه می‌دارد.

## پیش‌نیازها

- نصب **.NET SDK 8.0** (ترجیحاً آخرین نسخه اصلاح‌شده 8.0)
- دسترسی نوشتن به پوشه `App_Data` و زیرپوشه `App_Data/Backups`
- برای پروفایل محلی HTTPS، نصب و اعتماد گواهی توسعه‌ی localhost:

  ```powershell
  dotnet dev-certs https --trust
  ```

- برای migrationهای اختیاری EF Core، نصب بودن ابزار `dotnet-ef` نسخه 8.x

## restore، build و run

دستورات زیر را از ریشه پروژه اجرا کنید:

```powershell
dotnet restore
dotnet build
dotnet run --launch-profile https
```

پس از build می‌توان برنامه را بدون build مجدد اجرا کرد:

```powershell
dotnet run --no-build --launch-profile https
```

پروفایل `https` در `Properties/launchSettings.json` فقط روی `https://localhost:7079` اجرا می‌شود و محیط را `Development` قرار می‌دهد. پروفایل HTTP حذف شده است تا ورود محلی به‌صورت پیش‌فرض از HTTPS استفاده کند.

برای ساخت بدون restore:

```powershell
dotnet build --no-restore
```

## مسیر دیتابیس و نگهداری داده موجود

- اتصال پیش‌فرض در `appsettings.json` برابر است با:

  ```json
  "Data Source=App_Data/attendance.db"
  ```

- این مسیر نسبی است و هنگام اجرا نسبت به ریشه محتوای پروژه به مسیر مطلق تبدیل می‌شود؛ بنابراین فایل اصلی در `App_Data/attendance.db` قرار می‌گیرد.
- SQLite ممکن است فایل‌های موقت `attendance.db-wal` و `attendance.db-shm` را نیز ایجاد کند. این فایل‌ها بخشی از وضعیت دیتابیس هستند؛ هنگام اجرای برنامه آن‌ها را حذف، جابه‌جا یا جداگانه کپی نکنید.
- دیتابیس موجود را با حذف یا ساخت مجدد فایل تعویض نکنید. قبل از هر تغییر schema، توقف برنامه و تهیه backup الزامی است.
- در استقرار، مسیر دیتابیس را از طریق متغیر محیطی `ConnectionStrings__DefaultConnection` به محل مورد تأیید عملیات تغییر دهید. از قرار دادن مسیر یا رمز واقعی در این فایل‌ها خودداری کنید.

## seed حساب‌های آزمایشی

- seed فقط وقتی محیط `Development` است انجام می‌شود.
- `appsettings.json` مقدار `SeedAccounts:CreateDevelopmentAccounts` را `false` دارد و `appsettings.Development.json` آن را فقط برای Development برابر `true` می‌کند.
- اگر حتی یک کاربر در دیتابیس وجود داشته باشد، seed حساب جدیدی ایجاد نمی‌کند.
- در دیتابیس خالیِ Development، حساب‌های زیر ساخته می‌شوند:

  | نقش | نام کاربری | رمز آزمایشی |
  |---|---|---|
  | Admin | `admin` | `admin123` |
  | Operator | `operator` | `operator123` |

این نام‌های کاربری و رمزها فقط برای محیط Development و دیتابیس آزمایشی هستند و **محرمانه واقعی محسوب نمی‌شوند**. قبل از هر استقرار غیرتوسعه‌ای هر دو رمز را تغییر دهید، حساب‌های آزمایشی را در صورت عدم نیاز غیرفعال یا حذف کنید و رمزهای قوی یکتا را از طریق متغیرهای محیطی تأمین کنید؛ محتوای این فایل‌ها را در مخزن عمومی قرار ندهید.

اگر در محیط غیرتوسعه‌ای هیچ کاربری وجود نداشته باشد، برنامه عمداً خطا می‌دهد و به‌صورت خودکار حساب نمی‌سازد. قبل از شروع استقرار، یک حساب Admin فعال ایجاد کنید.

## نقش‌ها

- **Admin**: ورود به بخش‌های نیازمند احراز هویت، مدیریت کاربران و تهیه/دریافت backup.
- **Operator**: ورود به داشبورد، مدیریت افراد و واحدها، ثبت ورود و خروج و مشاهده گزارش‌ها.
- عملیات مدیریت کاربران و backup با نقش Admin محدود شده‌اند. کوکی‌ها `HttpOnly`، `SameSite=Lax` و متناسب با درخواست HTTPS هستند؛ بنابراین استقرار غیرتوسعه‌ای باید HTTPS را اجباری نگه دارد.

## backup

- کاربران Admin از مسیر `/Backup` می‌توانند نسخه پشتیبان ایجاد و فهرست کنند.
- فایل‌های backup در `App_Data/Backups/attendance-yyyyMMdd-HHmmss-fff.db` ساخته می‌شوند.
- سرویس backup از SQLite Backup API و اتصال مبدأ فقط‌خواندنی استفاده می‌کند. برای داده‌های حساس، هم‌زمان با backup عملیات نوشتاری را متوقف یا سیاست backup سازگار با بار کاری را اجرا کنید.
- backupها حاوی داده‌های حساس هستند؛ آن‌ها را رمزنگاری کنید، دسترسی را محدود کنید، در محل جداگانه/خارج از سایت نگهداری کنید و بازیابی را به‌طور دوره‌ای آزمایش کنید.
- فایل‌های backup را commit یا در مسیر عمومی وب قرار ندهید. هنگام بازیابی، ابتدا نسخه فعلی و فایل‌های WAL/SHM را حفظ کنید و سپس فرآیند بازیابی تأییدشده را اجرا کنید.

## schema غیرمخرب

برنامه در شروع کار به‌صورت زیر عمل می‌کند:

1. اگر هیچ‌یک از جدول‌های اصلی وجود نداشته باشد، `EnsureCreatedAsync` schema اولیه را می‌سازد.
2. اگر جدولی از قبل وجود داشته باشد، ستون‌های موردنیاز بررسی می‌شوند. در صورت کمبود ستون، برنامه قبل از هر تغییر متوقف می‌شود و خطای schema گزارش می‌کند.
3. ایندکس‌های یکتای نام کاربری، کد ملی و رکورد ورود باز با `IF NOT EXISTS` ساخته می‌شوند.
4. در صورت وجود نام کاربری تکراری، کد ملی تکراری یا چند رکورد ورود باز برای یک شخص، ساخت ایندکس خطا می‌دهد؛ داده‌ای حذف نمی‌شود.

در این نسخه migration از پیش‌ساخته‌ای وجود ندارد و startup برنامه به‌جای `MigrateAsync` از رفتار غیرمخرب بالا استفاده می‌کند. بنابراین دستور `dotnet ef database update` را بدون بررسی migration و backup روی دیتابیس موجود اجرا نکنید.

### فرآیند migration

برای تغییر schema:

1. برنامه را متوقف و از دیتابیس فعلی به‌همراه وضعیت SQLite یک backup قابل بازیابی بگیرید.
2. تغییر مدل را در شاخه جداگانه انجام دهید و migration را روی یک کپی از دیتابیس بسازید و بررسی کنید:

   ```powershell
   dotnet tool install --global dotnet-ef --version 8.0.19
   dotnet ef migrations add <MigrationName>
   dotnet ef database update
   ```

3. SQL تولیدشده باید افزاینده و سازگار با داده موجود باشد؛ جدول یا ستون موجود را بدون برنامه بازیابی حذف یا تغییر نوع ندهید.
4. migration را ابتدا روی کپی دیتابیس و سپس در محیط آزمایشی اجرا و بازیابی را آزمایش کنید.
5. در استقرار واقعی، نسخه پشتیبان، دستور migration، نتیجه بررسی و برنامه rollback را نگه دارید.

استفاده از migrationهای EF Core در برنامه نیازمند اضافه‌کردن فراخوانی `MigrateAsync` در لایه startup است؛ صرفاً ساخت فایل migration، رفتار startup فعلی را تغییر نمی‌دهد.

## خطاها و عیب‌یابی

- **Missing columns / schema is missing columns**: برنامه را متوقف کنید، backup را بررسی کنید و migration سازگار را اعمال کنید. دیتابیس را حذف یا بازسازی نکنید.
- **Duplicate users, national IDs, or open attendance records**: داده‌های تکراری را طبق قانون کسب‌وکار اصلاح کنید و سپس اجازه دهید ایندکس یکتا ساخته شود. هیچ داده‌ای خودکار حذف نمی‌شود.
- **Database is locked**: فرآیند یا نمونه دیگری که دیتابیس را باز کرده پیدا و متوقف کنید؛ فایل‌های WAL/SHM را حذف نکنید.
- **No user account exists**: در محیط غیرتوسعه‌ای یک حساب Admin فعال ایجاد کنید؛ seed خودکار فقط مخصوص Development است.
- **دسترسی به App_Data**: دسترسی نوشتن پوشه process را بررسی کنید؛ برنامه را بدون نیاز عملیاتی با دسترسی elevated اجرا نکنید.
- در Development از `UseDeveloperExceptionPage` استفاده می‌شود. در محیط‌های دیگر، صفحه عمومی `/Home/Error` نمایش داده می‌شود، HSTS فعال است و جزئیات استثنا برای کاربر افشا نمی‌شود.
- سطح پیش‌فرض log در استقرار `Warning` است. logها نباید رمز، کوکی، token یا داده حساس کاربران را ثبت کنند؛ تنظیم سطح Information فقط برای Development انجام شده است.
- مقدار پیش‌فرض `AllowedHosts` فقط localhost را مجاز می‌کند. در استقرار پشت reverse proxy یا دامنه عمومی، آن را از طریق تنظیمات میزبان به فهرست دقیق hostnameهای مورد تأیید محدود کنید و از مقدار `*` استفاده نکنید.

## امنیت استقرار

- HTTPS را در reverse proxy/سرور اجباری کنید و(cookie) را فقط در همین مسیر استفاده کنید.
- `ConnectionStrings__DefaultConnection`، رمز حساب‌ها و هر مقدار محرمانه دیگر را از environment/secret store تأمین کنید؛ هیچ مقدار محرمانه واقعی در `appsettings*.json` یا `launchSettings.json` قرار ندهید.
- `AllowedHosts` را به hostnameهای مورد تأیید محدود کنید.
- دسترسی فایل‌ای `App_Data` و `App_Data/Backups` را فقط به حساب اجرایی برنامه بدهید.
- قبل از انتشار، حساب‌های Development، رمزهای پیش‌فرض، Developer Exception Page و logهای سطح Information را بررسی و حذف/غیرفعال کنید.
